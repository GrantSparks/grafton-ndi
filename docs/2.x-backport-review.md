# Final 2.x bug fix release review

The best return is a small release built on `v2.0.0`, with targeted fixes for
unnecessary rebuilds, valid NV12 layouts, timeout handling, receiver status
polling, and Windows sender contention. Keep 2.0's public API, defaults,
build-time SDK linkage, and Rust 1.88 baseline. Do not backport PR #122 as a
whole, or use the current 3.0 implementations as replacements for 2.0 modules.

The scope is surgical fixes of clear bugs or concerns. Performance-only work,
new convenience APIs, new SDK features, and broad internal refactors are outside
this release, even when technically compatible with a minor version bump.

relevant SDK and platform runner are available. Small means roughly half a day
or less; medium means roughly one to two days. These are planning estimates,
not measured implementation times. Shared validation can reduce the total.

hardening, not evidence of an exploitable memory-safety defect: a length bound
does not make an invalid native pointer safe. A7 does not justify a release
on its own.

## Compatibility details that constrain the patches

### Timeouts

Do not cherry-pick `b7c95a1` wholesale. It touches new File, Discovery, and
Advanced APIs and changes the public maximum from `u32::MAX` milliseconds to
`u32::MAX - 1`. It also changes the meaning of `FrameTimeout.elapsed`.

For 2.x:

- Round positive durations upward when converting to SDK milliseconds;
  zero stays zero. Keep rejecting durations greater than the existing
  `MAX_TIMEOUT` with `Error::InvalidConfiguration`.
- Keep `MAX_TIMEOUT` and its accepted input range. To avoid passing the
  potential indefinite-wait sentinel, cap an individual native wait at
  `u32::MAX - 1` milliseconds. At the extreme boundary this shortens a single
  wait by at most one millisecond, consistent with its maximum-wait contract;
  retrying operations can use the remaining budget. Document and test this
  explicitly instead of silently refusing an input accepted by 2.0.
- Preserve existing deadlines across lock waits and blocking-pool queueing.
  Much of this already works in 2.0; it does not need a wholesale timeout
  subsystem replacement. Use checked instant arithmetic where a touched path
  currently adds a duration directly.
- Preserve `FrameTimeout.elapsed` as time in the retry loop, excluding time
  queued before it. The tag explicitly documents that behavior in
  `src/error.rs`; 3.0's different accounting is not a bug fix to that contract.
- Preserve `capture -> Result<Frame>`, its `FrameTimeout` error, and the
  `try_capture`/`try_capture_ref` single-poll contracts. A positive wait may
  round up by less than a millisecond; SDK and scheduler overruns remain
  possible, as already documented.

The shared timeout work in `2fbd3b5`, `8df11a1`, and the test correction
`e32d7b9` is useful reference material, not a dependency chain to import.

### Receiver status polling

A5 targets the 2.0 method `poll_status_change`, not the absent `poll_event`.
Each status-poll attempt should take pending status first, acquire the shared
guard within the caller's remaining budget, perform at most a 100 ms SDK wait,
release the guard, and recheck the remaining budget. Preserve error propagation
and notifications published while waiting. Zero timeout makes at most one
nonblocking attempt and does not wait for the guard.

Do not claim that every 2.x capture will release the guard within 100 ms:
`try_capture` and `try_capture_ref` deliberately make a single SDK call and may
hold it for their caller's timeout. Giving those methods the new 3.0 retry
semantics would change their documented behavior. The surgical fix eliminates
the status-poll stall; it does not redesign the whole capture API.

### Bounded source and version strings

Use the 3.0 bound of 4 MiB including the terminator, with a shared scanner that
stops at the first NUL. Keep existing null handling, source address
classification, lossy source-name/address decoding, and strict UTF-8 for
`NDI::version()`. Keep Finder's snapshot lock held through the copies and keep
skipping only malformed entries. Preserve `Source` fields, `SourceAddress::None`,
`SourceCache::find_by_host` and `NDI::version() -> Result<String>`.

There is no suitable general malformed-SDK-result variant in 2.0's `Error`.
The clean small adaptation is to add `UnexpectedSdkResult(String)` solely for
the new over-limit rejection. `Error` is already `#[non_exhaustive]`, so this
does not require downstream exhaustive matches to change. Keep all existing
variants and existing error cases. Use **2.1.0** if including this public error
addition, as the conservative versioning choice. Do not mislabel an over-limit
string as invalid UTF-8 or a null pointer just to avoid adding a variant.

The new limit rejects strings that 2.0 could previously accept; record that
defensive behavior in release notes. The scanner still requires readable native
storage up to its terminator or the bound. Test with valid allocated storage,
including a terminator at the last allowed byte and one beyond it.

### Sender synchronization

A3 needs no generic sender modes, shared native owner, or proof-token framework.
All 2.0 flush callers already hold the sender's video lock or exclusive access
during destruction. Preserve completion-handler ordering, panic/reentry
behavior, and recovery of owned frames. The later `9c0b421` refactor changes
drop-time callback ordering and is especially unsuitable for a blind backport.

## Changes that do not belong in 2.x

- Runtime loading, vendored bindings, capability tables, two-stage runtime
  selection, new library search order, process-lifetime initialization, and the
  changed missing-library behavior (`2026135`, `f5cd3fb`, `67267fd`, `c8cdb19`).
- Public renames, private option/source/status fields, builder removal, unsigned
  dimensions, typed timecodes/frame rates, changed errors, altered default
  features, removal of `advanced_sdk`, or narrowed Tokio feature propagation
  (`20007bc` and related commits).
- Removing raw audio from `Receiver<FrameSyncAttached>`, replacing the FrameSync
  request API, changing capture result types, changing `tally`'s signature, or
  changing `SourceCache::find_by_host` to require an NDI argument.
- File recording/playback and all its shutdown, cancellation, queue, path,
  rollover and owner-failure fixes: these APIs do not exist in 2.0.
- Advanced allocators, compressed/scatter/queued senders, packet receivers,
  AvSync, Genlock, and KVM, including their ownership, thread-trait and callback
  fixes: these APIs do not exist in 2.0. `advanced_sdk` is only a compatibility
  flag in the tag, not these features.
- Discovery Server advertisers/listeners, routing and capability-dependent
  configuration fixes: likewise new APIs. The shared source-string issue is
  extracted separately as A6.
- `VideoConverter`'s unaligned P216 fix (`6a3472b`): the converter is new. Do not
  mistake that fix for a defect in the existing 2.0 frame layout implementation.
- New 4:4:4 formats, video-only bandwidth modes, interleaved conversion APIs,
  Apple mobile targets and new SDK feature qualification.

## Release plan and validation proportional to the changes

1. Apply A1 and A2 as individual backports. Both dry-run cleanly against the
   base; successful patch application is not a substitute for their tests.
2. Port A3's Windows lock removal, retaining the old native call path. Run the
   existing ownership/panic/reentry tests and a concurrent multi-sender test
   with a watchdog on Windows.
3. Implement A4's rounding/boundary changes and A5's status-poll loop without
   replacing modules. Test zero/sub-millisecond/maximum/over-limit durations,
   lock contention, retained notifications, SDK errors, early returns and a
   reconnect waiting behind a long status poll. Prefer deterministic budget
   assertions over brittle wall-clock upper bounds.
4. Add A6/A7 and the documentation corrections if including bounded text.
   Verify null/empty/invalid-UTF-8 behavior and exact size boundaries, including
   Finder's mixed valid/invalid snapshot and `NDI::version`'s old signature.
5. Run the existing 2.x formatting, lint, MSRV, public compile-contract and
   core SDK suites. Check default, no-default, Tokio, smol, and `advanced_sdk`
   configurations. Run relevant capture/send regressions on Linux and Windows,
   with the existing macOS checks. Use the retained 6.3.2 baseline; do not claim
   that 3.0's tests qualify the resulting 2.x artifact against other runtimes.
6. Compare API compatibility explicitly with `v2.0.0`, including auto traits of
   touched types and old downstream examples. Do not let a latest-release
   lookup compare the maintenance branch against a future published 3.x.
7. Generate a 2.x changelog and version only after the actual set is settled.
   For A1–A5 plus documentation/log cleanup, **2.0.1** is the appropriate narrow
   target. With the small new A6 error variant, **2.1.0** is the conservative
   target. Neither requires importing any 3.0 feature.

The versioning distinction follows the [SemVer specification](https://semver.org/spec/v2.0.0.html):
compatible fixes permit a patch; compatible public additions permit a minor.
The [Cargo compatibility guide](https://doc.rust-lang.org/cargo/reference/semver.html)
also distinguishes API compatibility from runtime behavior, which still needs
explicit review. Passing an API diff alone cannot establish compatibility.

Limit CI changes to what makes this branch and its regression tests reliable.
Enable maintenance-branch validation and pin the comparison baseline. Keep SDK
installation and libclang: 2.0 still needs both. Reuse Windows loopback test
lessons from `501923d` only if a test encounters the same SDK stream-reuse stall;
these are test-fixture fixes, not a crate fix to advertise to users.

Do not copy the 3.0 publishing workflow unchanged. It checks that the tag is an
ancestor of `main`, which would reject a divergent 2.x backport release, and its
package verification assumes the new build model. Review the existing 2.x
publication path and documentation destination when preparing the release;
avoid replacing newer API documentation with an unversioned maintenance build.
The broader CI acquisition/decoder/packaging overhaul is not a prerequisite for
these small code fixes.
