# Migrating from 1.x to 2.0

Update the dependency to `grafton-ndi = "2.0"`. Feature names and the minimum
Rust version (1.87) are unchanged. This release requires a major version because
`NDI` can no longer be constructed directly and async sends now take ownership
of `VideoFrame`. It also changes async-send memory costs and corrects several SDK layout contracts.

## Runtime handles

Replace direct unit construction (`let ndi = NDI;`) with checked initialization:

```rust
use grafton_ndi::NDI;

fn main() -> Result<(), grafton_ndi::Error> {
    let ndi = NDI::new()?;
    let another_handle = ndi.clone();
    drop(another_handle);
    drop(ndi);
    Ok(())
}
```

Each constructed or cloned handle owns a runtime reference. Sender, receiver,
and finder constructors still accept `&NDI` and keep their own live handles.

## Async video sends take ownership

`Sender::send_video_async` now takes a `VideoFrame` by value and returns
`Option<VideoFrame>` instead of a token. The sender retains the submitted frame
while the SDK uses its pixels and metadata. A subsequent send synchronizes the
previous submission and returns that completed frame for reuse. Moving a frame
does not allocate or copy its pixel buffer.

Use two frames to overlap rendering with transmission:

```rust
use grafton_ndi::{Sender, SenderOptions, VideoFrameBuilder, NDI};

fn main() -> Result<(), grafton_ndi::Error> {
    let ndi = NDI::new()?;
    let options = SenderOptions::builder("Owned async sender").build();
    let mut sender = Sender::new(&ndi, &options)?;
    let first = VideoFrameBuilder::new().build()?;
    let mut available = VideoFrameBuilder::new().build()?;
    assert!(sender.send_video_async(first).is_none());
    for value in 0..60u8 {
        available.data_mut().fill(value);
        available = sender.send_video_async(available).expect("previous frame");
    }
    let final_frame = sender.finish_video_async().expect("final frame");
    drop((available, final_frame));
    Ok(())
}
```

`finish_video_async()` submits the SDK's null-frame synchronization boundary and
returns the final owned frame. Sender destruction also drains pending work.
`flush_async_blocking()` completes transmission but retains the owned frame for
recovery by the next send or finish. The misleading `flush_async(timeout)` method
is removed: use `flush_async_blocking()` when you need explicit synchronization,
or `finish_video_async()` when you also need the final owned frame back. These
SDK synchronization calls block until completion and have no timeout argument.

For borrowed application buffers, rename the old call to
`send_video_async_copy(&borrowed_frame)`. This explicit convenience allocates and
copies pixels and optional metadata into sender-owned storage and returns the
existing `AsyncVideoToken`; wait or drop it to observe completion. Forgetting a
token remains memory-safe because the sender retains the copied storage, but
skips its user completion notification. The copied snapshot can remain allocated
until the next send or sender destruction. Mixing owned and copying sends is
supported; replacing a copied snapshot returns `None`, since no owned frame is
available to return.

`AsyncVideoToken::is_complete` and the public `waitable_completion` module are
removed. Completion is observed at a subsequent
send, explicit finish/flush, token wait/drop, or sender destruction. The optional
`on_async_video_done` handler runs on the calling thread when completion is
observed, once per submission. No SDK completion callback is registered, even
with `advanced_sdk`. This retained compatibility flag has no effect on sender
completion; it does not enable additional Advanced-only functionality. Do not
wait for a callback before submitting the next frame.
Borrowed receive APIs remain zero-copy. The unsafe `from_parts_unchecked`
escape hatch still requires all SDK payload invariants, including valid external
storage.

## Video widths and multi-plane layouts

Every supported uncompressed pixel format now requires a positive **even
width**, including BGRA, BGRX, RGBA, and RGBX. Crop or pad odd-width input before
building frames. Sizing helpers and receive validation enforce the same rule.
Planar and semi-planar 4:2:0 formats retain their even-height requirements.

For UYVA, P216, and PA16, `try_line_stride()` describes the first plane rather
than aggregate bytes across all planes. `info().bytes_per_pixel()` now returns
`2` for these formats (previously `3`, `4`, and `4`, respectively).

| Format | Tight first-plane stride | Plane layout | Tight total buffer size |
| --- | --- | --- | --- |
| UYVA | `2 * width` | UYVY, then 8-bit alpha with half the first-plane stride | `3 * width * height` |
| P216 | `2 * width` | 16-bit Y, then interleaved 16-bit CbCr at the same stride | `4 * width * height` |
| PA16 | `2 * width` | P216 planes, then 16-bit alpha at the same stride | `6 * width * height` |

Use `PixelFormat::try_buffer_size` or `PixelFormatInfo::try_buffer_len` for
allocation. Multiplying width, height, and `bytes_per_pixel()` omits extra
planes. For padded frames, pass the actual first-plane stride to the checked
layout APIs. `FormatCategory` now also exposes `PackedAlpha`, `SemiPlanar422`,
and `SemiPlanar422Alpha`; keep a wildcard arm when matching this non-exhaustive
enum. Owned and borrowed receive validation use these corrected plane sizes.

## Borrowed frame customization

Borrowed frames can set timecode and aspect ratio without using the unsafe raw
constructor:

```rust
use grafton_ndi::{BorrowedVideoFrame, PixelFormat};

fn main() -> Result<(), grafton_ndi::Error> {
    let pixels = vec![0; 1920 * 1080 * 4];
    let frame = BorrowedVideoFrame::try_from_uncompressed(
        &pixels, 1920, 1080, PixelFormat::BGRA, 30, 1,
    )?
    .with_timecode(10_000_000)
    .with_picture_aspect_ratio(0.0)?;
    assert_eq!(frame.timecode(), 10_000_000);
    Ok(())
}
```

Timecodes use 100 ns units. Explicit zero remains a literal timecode; the default
requests SDK synthesis. Aspect ratio `0.0` selects square pixels; negative,
non-finite ratios are rejected. The borrowed constructor still defaults to 16:9.

## Discovery and async timeouts

Finder source snapshots now hold a per-finder lock from SDK retrieval through
copying into owned sources. Concurrent snapshot calls on one finder serialize;
public method signatures stay the same.

For both Tokio and async-std adapters, `capture` and `try_capture` validate the
timeout before scheduling blocking work. The budget starts when the future is
first polled and includes time queued in the blocking pool. Queue delay reduces
the remaining SDK wait. This is a wait budget, not a wall-clock completion
deadline: queued work can still finish after the budget expires. Code requiring
a response deadline should account for that separately.
