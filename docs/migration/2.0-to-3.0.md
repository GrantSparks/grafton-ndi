# Migrating from 2.0 to 3.0

Update the dependency to `grafton-ndi = "3.0"`. The minimum Rust version is
still 1.88.

Version 3.0 is a breaking release. Version 2.0 linked the NDI library when
your program was built; 3.0 loads it when your program selects a runtime. That
removes the NDI SDK from the build, turns a missing library from a start-up
failure into an ordinary Rust error, and gives the search for the library a
defined order. With it, one public signature changed and two functions and one
Cargo feature were removed.

3.0 works with NDI 6 runtimes and was tested against the Standard 6.1.1 and
the Standard and Advanced 6.3.2 and 6.4.0.2 runtimes; the
[README](../../README.md#supported-ndi-versions-and-platforms) lists what each
provides and the supported platforms.

This guide starts with what you must change, then follows the order in which
you will meet the rest: building, running, errors, and deploying.

## What you must change

These things from 2.0 no longer compile, resolve or link.

**`SourceCache::find_by_host` takes the runtime handle.** The cache no longer
starts NDI by itself:

```diff
 let ndi = NDI::new()?;
 let cache = SourceCache::new();
-let camera = cache.find_by_host("192.168.1.100", Duration::from_secs(5))?;
+let camera = cache.find_by_host(&ndi, "192.168.1.100", Duration::from_secs(5))?;
```

**`NDI::is_supported_cpu()` is removed.** The question belongs to a selected
runtime, which answers it without starting NDI:

```diff
-if !NDI::is_supported_cpu() {
+let runtime = Runtime::select(&RuntimeOptions::default())?;
+if !runtime.is_supported_cpu() {
     eprintln!("this CPU cannot run NDI");
 }
```

With a handle already in hand, use `ndi.runtime().is_supported_cpu()`.
Selecting pins the library for the rest of the process, so select with the
options the program will start NDI with: a later `NDI::with_options` that
names another library returns `Error::RuntimeConflict`.

**`NDI::version()` is removed.** The version is part of the runtime's identity:

```diff
-let version = NDI::version()?;
+let version = ndi.info().raw_version();
```

`raw_version` returns a `&'static str`; add `.to_owned()` where a `String` is
needed. Before NDI is started, use
`Runtime::select(&RuntimeOptions::default())?.info().raw_version()`.

**The `advanced_sdk` Cargo feature is removed.** It had no effect in 2.0.
Delete it from your manifest:

```diff
-grafton-ndi = { version = "2.0", features = ["advanced_sdk"] }
+grafton-ndi = "3.0"
```

**APIs that did nothing, or did one thing twice, are removed or narrowed:**

```diff
-let host = source.ip_address();
+let host = source.host();

-if let Some(status) = receiver.poll_status_change(timeout)? {
+if let Some(ReceiverEvent::StatusChanged(status)) = receiver.poll_event(timeout)? {

-let stride = match frame.line_stride_or_size() {
-    LineStrideOrSize::LineStrideBytes(stride) => stride as usize,
-};
+let stride = frame.line_stride_bytes();

-receiver.ptz_store_preset(3_i32)?;
+receiver.ptz_store_preset(3_u8)?;

-let audio = AudioFrameBuilder::new().format(AudioFormat::FLTP)
+let audio = AudioFrameBuilder::new()
```

- `Source::host` returns what `ip_address` did, which for a URL source is a
  host name.
- `poll_event` also returns the source-change events that `poll_status_change`
  skipped, so match the variant you want. With one poller, two no longer
  compete for the same notification.
- `ptz_store_preset` and `ptz_recall_preset` both take the preset as a `u8`
  in `0..=99`.
- FLTP is the only audio format and every audio frame uses it.

**Five error variants are removed.** `Error::SourceUnavailable`,
`Error::Disconnected` and `Error::Io` were never returned. Delete `match` arms
that name them. Code that used `?` to turn a `std::io::Error` into a
`grafton_ndi::Error` needs an error type of its own, such as
`Box<dyn std::error::Error>`. `Error::Timeout` and `Error::PtzCommandFailed`
reported that the SDK refused an operation, which is now
`Error::NativeOperationFailed`, as for the operations new in 3.0.

**The `tokio` feature enables only Tokio's `rt` feature.** If your program uses
`#[tokio::main]` or the multi-threaded runtime and relied on this crate to
enable them, enable them in your own dependency:

```toml
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
```

**The build no longer links the NDI library** for Windows, macOS, Linux and
Android targets; 2.0 passed it to the linker. Code that declares its own NDI
functions with `extern "C"`, and C or C++ code that calls NDI, must now link
the library itself, for example with its own `cargo:rustc-link-lib`. Calls made
through this crate need nothing: it opens the library at run time and does not
make its symbols visible to the rest of the program.

Two results of `NDI::new()` changed:

- A missing NDI library is `Error::RuntimeLoadFailed` from `NDI::new()`. With
  2.0 the program did not start.
- A runtime that does not start because the CPU lacks instructions it needs is
  `Error::UnsupportedCpu`. With 2.0 it was `Error::InitializationFailed`.

A finder, receiver, sender or FrameSync that the SDK does not create is
`Error::NativeOperationFailed`, whose `operation` names the creating function,
such as `"NDIlib_send_create"`. With 2.0 it was `Error::InitializationFailed`.

`ReceiverOptions::default()` now allows video fields, as
`ReceiverOptions::builder` and the SDK always did. Set
`allow_video_fields: false` to keep 2.0's behaviour.

`Error` has six new variants, listed under [New errors](#new-errors). The enum
was already `#[non_exhaustive]`, so a `match` on it already has a wildcard arm
and keeps compiling unless it names one of the removed variants.

The library search order changed as well, and it now looks for either SDK
edition; see [Where the library is found](#where-the-library-is-found) and
[Both editions are searched for](#both-editions-are-searched-for). Everything else in 3.0 is an
addition: runtime selection and capability queries, routing, Discovery Server
objects, NDI 6.4 formats and receiver controls, checked audio and video
conversions, and the optional `advanced` and `file` modules (Cargo features
`advanced` and `file-io`). The [README](../../README.md) introduces each one.

## Building

A 2.0 build ran bindgen against an installed NDI SDK and linked the SDK's
library. A 3.0 build for Windows, macOS, Linux or Android does neither, unless
the `advanced` feature finds an Advanced SDK, in which case it runs bindgen on
that SDK's Advanced-only headers. The other bindings are part of the crate.

- Build machines and CI jobs that only compile no longer need the NDI SDK or
  LLVM/`libclang`, except to build the `advanced` feature's native code. A
  machine needs an NDI runtime library only where tests or the program itself
  use NDI.
- What is installed on the build machine no longer changes the program. A
  2.0 build on a machine with the Advanced SDK linked the Advanced library; a
  3.0 program looks for the library of either edition when it runs; see
  [Both editions are searched for](#both-editions-are-searched-for).
- Cross-compiling needs no target SDK. Version 2.0 refused to cross-compile
  without `NDI_SDK_DIR`; 3.0 does not need it for these targets.
- The documentation builds without an SDK. The crate's API reference link now
  points to [docs.rs](https://docs.rs/grafton-ndi).

`NDI_SDK_DIR` is read at build time only by two kinds of build:

1. A build with the `advanced` feature, to find the Advanced SDK headers.
2. A build for iOS, tvOS or visionOS, to find the static library. Support for
   these targets is new in 3.0; they link NDI at build time and require the
   variable.

Every other build ignores it, so a value left over from 2.0 no longer matters
there. In the two builds that read it, a set `NDI_SDK_DIR` must name an NDI SDK
installation: a directory whose `include` (or `Include`) directory contains
`Processing.NDI.Lib.h`, the spelling the NDI SDK installers use. A stale value
fails those builds:

```text
NDI_SDK_DIR is not an NDI SDK installation: Cannot read SDK directory /old/path: No such file or directory (os error 2)
```

Unset the variable on machines that no longer have an SDK. When it is unset,
an `advanced` build looks only in the Advanced SDK installer's default
directory, no longer in the Standard SDK's, and continues without the Advanced
declarations if it finds none. It does not notice an SDK that is installed
there after the first build.
Set `NDI_SDK_DIR`, which triggers a rebuild, or run `cargo clean -p grafton-ndi`.

## Running

### Selecting and starting are separate steps

Using NDI takes two steps. `Runtime::select` loads the NDI library and pins it
for the rest of the process, without starting NDI. `Runtime::initialize` starts
NDI and returns the `NDI` handle. `NDI::new()` does both with the default
options, and `NDI::with_options` with the options it is given, so code that
only calls `NDI::new()` needs no change.

Nothing else selects a runtime. `NDI::is_running()`, for one, loads nothing.

Selecting first lets a program inspect the library before it starts NDI:

```rust
use grafton_ndi::{Runtime, RuntimeOptions};

fn main() -> grafton_ndi::Result<()> {
    let runtime = Runtime::select(&RuntimeOptions::default())?;
    println!("NDI {}", runtime.info().raw_version());
    if !runtime.is_supported_cpu() {
        eprintln!("this CPU cannot run the selected NDI runtime");
    }
    let ndi = runtime.initialize()?;
    println!("started: {ndi:?}");
    Ok(())
}
```

### A missing runtime is an error value

With 2.0, a program whose NDI library could not be found did not start: the
operating system's loader stopped it before `main` ran. With 3.0 the program
starts, and a library that cannot be found is reported by the call that
selects it:

```rust
use grafton_ndi::{Error, NDI};

fn main() {
    match NDI::new() {
        Ok(ndi) => println!("NDI {} is ready", ndi.info().raw_version()),
        Err(Error::RuntimeLoadFailed(reason)) => {
            // `reason` lists every location tried and why each failed.
            eprintln!("NDI is not installed: {reason}");
        }
        Err(Error::UnsupportedCpu) => eprintln!("NDI cannot run on this CPU"),
        Err(error) => eprintln!("NDI could not be initialized: {error}"),
    }
}
```

This lets an application start without NDI and offer it as an optional
feature. Selection is retryable: if the first attempt fails, a later call
searches again, so a program can ask the user to install the runtime and try
once more.

### Where the library is found

Version 2.0 left the search to the operating system: the executable's run path,
`LD_LIBRARY_PATH` or `PATH`, and the system library directories. Version 3.0
tries these locations in order and takes the first usable library:

1. The directory that contains the running executable.
2. The directory named by the `NDI_RUNTIME_DIR_V6` environment variable.
3. The operating system's search, as in 2.0. On macOS the name is first tried
   as `@rpath/<name>`.

A setup that worked with 2.0 keeps working through step 3, with one difference
to check: steps 1 and 2 now come first. If `NDI_RUNTIME_DIR_V6` is set on a
machine, the library in that directory is used even when a different one is
on the loader's path. `ndi.info().library_path()` reports which file was
loaded.

A plug-in or extension module is the exception. Step 1 is the host program's
directory, not the plug-in's, and on Windows step 3 does not search the
plug-in's directory either, so a library that 2.0 found beside the plug-in may
not be found. Set `NDI_RUNTIME_DIR_V6`, or pass the library's path as shown
under [Deploying](#deploying).

The error for a failed search names each location:

```text
Failed to load the NDI runtime: no usable NDI runtime; tried /opt/app/libndi.so.6 (next to the executable): not found; /opt/app/libndi_advanced.so.6 (next to the executable): not found; libndi.so.6 (system library search): dlopen failed: libndi.so.6: cannot open shared object file: No such file or directory; libndi_advanced.so.6 (system library search): dlopen failed: libndi_advanced.so.6: cannot open shared object file: No such file or directory
```

### One library per process

The first library that is selected successfully stays selected, and loaded,
for the life of the process, including after the last `NDI` handle is dropped.
Starting and stopping NDI still follow the handles as in 2.0. Asking for a
different library afterwards returns `Error::RuntimeConflict`.

### Both editions are searched for

The Standard and Advanced SDKs have different library file names, for example
`libndi.so.6` and `libndi_advanced.so.6` on Linux. Unless the program asks for
one edition, each location in the search is tried for both names before the
next location, so the program finds whichever runtime the machine has. A build
with the `advanced` feature, or with `file-io` on Linux, macOS or Android, where
the File library needs the Advanced runtime, tries the Advanced name first at
each location; other builds try the Standard name first.

Version 2.0 on Linux and Android linked the Advanced library when the build
machine had the Advanced SDK, and such a program needed the Advanced runtime
wherever it ran. A 3.0 program built on the same machine also runs where only
the Standard runtime is installed. A program that needs Advanced SDK
operations should say so, and fail at selection instead of later:

```rust
use grafton_ndi::{RuntimeOptions, SdkEdition, NDI};

fn main() -> grafton_ndi::Result<()> {
    let options = RuntimeOptions::default().edition(SdkEdition::Advanced);
    let ndi = NDI::with_options(&options)?;
    println!("loaded the {:?} runtime", ndi.info().edition());
    Ok(())
}
```

Requesting `SdkEdition::Advanced` searches only for the Advanced file name and
requires the loaded library to be an Advanced SDK runtime. Requesting
`SdkEdition::Standard` searches only for the Standard file name; an Advanced
runtime found under it meets a Standard request.

### A rejected library stays loaded

A library that loads and is then found unusable is rejected, and the search
moves on. The rejected library stays loaded, because a native library cannot
be unloaded safely. If the operating system's own search in step 3 then
matches the library name to that rejected module, it returns the module again
instead of looking further. The error names the rejected file. Remove or fix
that file, or select the right one with an explicit path as shown under
[Deploying](#deploying).

## New errors

Every variant below is new in 3.0.

| Variant | Returned when |
| --- | --- |
| `RuntimeLoadFailed` | No usable NDI library could be loaded. Returned by `Runtime::select`, `NDI::new` and `NDI::with_options`. |
| `RuntimeConflict` | `Runtime::select` or `NDI::with_options` names a library other than the one already selected, or requires the Advanced SDK when the selected library is a Standard one. |
| `UnsupportedCpu` | The runtime did not start and reports that this CPU cannot run it. Returned by `Runtime::initialize`, `NDI::new` and `NDI::with_options`. |
| `UnsupportedCapability` | An optional operation is not available with the selected library or in this build. The error names the capability and the reason. |
| `RuntimeRequired` | A planar 4:4:4 video frame is built with `build()` instead of `build_for(&ndi)`, by `VideoFrameBuilder` or `BorrowedVideoFrameBuilder`. Those formats need a runtime that supports them. |
| `NativeOperationFailed` | The SDK refused an operation, such as a PTZ command, a routing change or an advertiser registration, or did not create a finder, receiver, sender or other object. `operation` names the SDK function. |

Operations that existed in 2.0 use only functions that every supported NDI 6
library exports. They do not return `UnsupportedCapability`. A library that
lacks one of those functions is rejected when it is selected.

`Error::InitializationFailed` now means only that the library loaded and the
SDK refused to start, for any reason other than the CPU, or that the process
holds so many `NDI` handles that their count would overflow. An object the SDK
does not create is `Error::NativeOperationFailed`, and a Discovery Server
address it refuses is `Error::InvalidConfiguration`.

## Deploying

The executable no longer lists the NDI library among its dependencies. Tools
that collect a program's libraries by inspecting the executable will not find
it, so add the NDI library to your package explicitly. Three arrangements
work, and they can be combined:

- **Ship the library beside the executable.** Put the file with the name from
  the [README table](../../README.md#finding-the-runtime) in the executable's
  directory. It is found first, whatever else is installed.
- **Use an installed runtime.** Set `NDI_RUNTIME_DIR_V6` to the runtime's
  directory, or install the library where the operating system's loader finds
  it.
- **Name the file.** Pass an absolute path. Nothing else is tried, so a wrong
  path is reported instead of being hidden by a fallback:

```rust
use grafton_ndi::{RuntimeOptions, NDI};

fn main() -> grafton_ndi::Result<()> {
    let options = RuntimeOptions::default().library_path("/opt/ndi/lib/libndi.so.6");
    let ndi = NDI::with_options(&options)?;
    println!("loaded {:?}", ndi.info().library_path());
    Ok(())
}
```

Loading a library runs its native code. Load only NDI libraries you trust. The
search reads `NDI_RUNTIME_DIR_V6` and the executable's directory, so a program
that runs with privileges its user does not have should pass an explicit path.

## Tests and continuous integration

Tests that use NDI now need the runtime only when they run. A job that only
builds, lints or documents your crate needs no NDI installation at all. A job
that runs NDI tests needs the runtime library in one of the locations above,
for example through `NDI_RUNTIME_DIR_V6`.

## Optional capabilities

NDI libraries differ in what they export, and the new APIs check before they
call. To check yourself, ask the selected runtime:

```rust
use grafton_ndi::{RuntimeFeature, NDI};

fn main() -> grafton_ndi::Result<()> {
    let ndi = NDI::new()?;
    if ndi.capabilities().supports(RuntimeFeature::ReceiveDelay) {
        println!("receiver delay controls are available");
    }
    // Or fail with the reason.
    ndi.require_feature(RuntimeFeature::Routing)?;
    Ok(())
}
```

See [Runtime capabilities](../../README.md#runtime-capabilities-and-optional-apis)
in the README for the list and what each reason means.
