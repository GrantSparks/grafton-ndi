# Migrating from 2.0 to 3.0

Update the dependency to `grafton-ndi = "3.0"`. The minimum Rust version is
still 1.88.

Version 3.0 is a breaking release in two ways. Version 2.0 linked the NDI
library when your program was built; 3.0 loads it when your program selects a
runtime. That removes the NDI SDK from the build, turns a missing library from
a start-up failure into an ordinary Rust error, and gives the search for the
library a defined order. And the public API now follows one set of
conventions: Rust casing, options types with chainable setters, unsigned
dimensions and counts, typed timecodes and frame rates, one error type, and
captures that report a timeout as `None`.

Most of the changes stop 2.0 code from compiling, so the compiler finds them.
Where a 2.0 call still compiles with a different meaning, or its replacement
does not behave exactly like it, this guide says so:
[FrameSync's captures](#framesync), [`try_capture`](#receiving),
[`ReceiverOptions::default()`](#options) and
[`BorrowedVideoFrame::data`](#sending).

3.0 works with NDI 6 runtimes and was tested against the Standard 6.1.1 and
the Standard and Advanced 6.3.2 and 6.4.0.2 runtimes; the
[README](../../README.md#supported-ndi-versions-and-platforms) lists what each
provides and the supported platforms.

This guide starts with what you must change, then follows the order in which
you will meet the rest: building, running, errors, and deploying.

## What you must change

These things from 2.0 no longer compile, resolve or link, or now behave
differently. The snippets show 2.0 code as removed lines and its 3.0
replacement as added lines.

### Dependency and features

**Image encoding is opt-in.** `image-encoding` is no longer a default feature,
and the crate has no default features. If you call `encode_png`,
`encode_jpeg` or `encode_data_url`, or use `ImageFormat`, enable it:

```toml
grafton-ndi = { version = "3.0", features = ["image-encoding"] }
```

A manifest that already set `default-features = false` needs no change for
this.

**The `advanced_sdk` Cargo feature is removed.** It had no effect in 2.0.
Delete it from your manifest:

```diff
-grafton-ndi = { version = "2.0", features = ["advanced_sdk"] }
+grafton-ndi = "3.0"
```

**The `tokio` feature enables only Tokio's `rt` feature.** If your program uses
`#[tokio::main]` or the multi-threaded runtime and relied on this crate to
enable them, enable them in your own dependency:

```toml
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
```

### Names

**`NDI` is `Ndi`, and acronyms are written as one word.** Identifiers follow
Rust's casing rules. Prose and the SDK's own names still say NDI:

```diff
-use grafton_ndi::{AudioFormat, PixelFormat, ReceiverColorFormat, NDI};
+use grafton_ndi::{AudioFormat, Ndi, PixelFormat, ReceiverColorFormat};

-let ndi = NDI::new()?;
+let ndi = Ndi::new()?;
-let format = PixelFormat::BGRA;
+let format = PixelFormat::Bgra;
-let color = ReceiverColorFormat::UYVY_BGRA;
+let color = ReceiverColorFormat::UyvyBgra;
-let audio = AudioFormat::FLTP;
+let audio = AudioFormat::Fltp;
```

The pixel formats are `Uyvy`, `Uyva`, `P216`, `Pa16`, `Yv12`, `I420`, `Nv12`,
`Bgra`, `Bgrx`, `Rgba` and `Rgbx`. The receiver color formats are `BgrxBgra`,
`UyvyBgra`, `RgbxRgba` and `UyvyRgba`; `Fastest` and `Best` keep their names.

**The async receivers moved to the `asynchronous` module:**

```diff
-use grafton_ndi::tokio::AsyncReceiver;
+use grafton_ndi::asynchronous::tokio::AsyncReceiver;
```

`grafton_ndi::smol` is `grafton_ndi::asynchronous::smol` in the same way. The
crate root has no `tokio` or `smol` module any more, so `use grafton_ndi::*`
no longer shadows the crates of those names. `asynchronous::AsyncReceiver<R>`
and `asynchronous::AsyncCapture<'rx, R, K>` are generic over the runtime
markers `Tokio` and `Smol`, and the `tokio` and `smol` modules name both types
for one runtime. Their captures changed as described under
[Receiving](#receiving).

### Runtime

**`NDI::is_supported_cpu()` is removed.** The question belongs to a selected
runtime, which answers it without starting NDI:

```diff
-if !NDI::is_supported_cpu() {
+let runtime = Runtime::select(&RuntimeOptions::default())?;
+if !runtime.is_supported_cpu() {
     eprintln!("this CPU cannot run NDI");
 }
```

With a handle already in hand, use `ndi.runtime().is_supported_cpu()`.
Selecting pins the library for the rest of the process, so select with the
options the program will start NDI with: a later `Ndi::with_options` that
names another library returns `Error::RuntimeConflict`.

**`NDI::version()` is removed.** The version is part of the runtime's identity:

```diff
-let version = NDI::version()?;
+let version = ndi.info().raw_version();
```

`raw_version` returns a `&'static str`; add `.to_owned()` where a `String` is
needed. Before NDI is started, use
`Runtime::select(&RuntimeOptions::default())?.info().raw_version()`.

### Options

**Options are set with chainable setters; the options builders are removed.**
`FinderOptions`, `ReceiverOptions` and `SenderOptions` have private fields, a
constructor that takes what they require, and a setter for everything else.
`FinderOptionsBuilder`, `ReceiverOptionsBuilder`, `SenderOptionsBuilder` and
the `builder()` functions that returned them are removed:

```diff
-let finder_options = FinderOptions::builder().show_local_sources(false).build();
+let finder_options = FinderOptions::new().show_local_sources(false);

-let receiver_options = ReceiverOptions::builder(source.clone())
-    .color(ReceiverColorFormat::RGBX_RGBA)
-    .name("Monitor")
-    .build();
+let receiver_options = ReceiverOptions::new(source.clone())
+    .color_format(ReceiverColorFormat::RgbxRgba)
+    .name("Monitor");

-let snapshot = ReceiverOptionsBuilder::snapshot_preset(source).build();
+let snapshot = ReceiverOptions::snapshot_preset(source);

-let sender_options = SenderOptions::builder("Camera 1").clock_audio(false).build();
+let sender_options = SenderOptions::new("Camera 1").clock_audio(false);
```

- Struct literals and field reads no longer compile. A required value is the
  argument of `new`: `SenderOptions`' `name` and `ReceiverOptions`'
  `source_to_connect_to`. Every other field is set with the setter of the same
  name, except `ReceiverOptions`' `ndi_recv_name`, which is set with `name`.
  The receiver builder's `color` is `color_format`.
- The defaults are 2.0's: a finder includes local sources, a sender clocks
  video and audio, and a receiver uses `BgrxBgra` at the highest bandwidth.
- `ReceiverOptions` no longer implements `Default`, because it needs a source.
  `ReceiverOptions::new` allows video fields, as 2.0's builder and the SDK do;
  2.0's `ReceiverOptions::default()` did not. Add `.allow_video_fields(false)`
  where you need that.

### Sources and status values

**`Source` has private fields.** Create one with `Source::new` and read it with
`name()` and `address()`:

```diff
-let source = Source {
-    name: "CAMERA (Program)".into(),
-    address: SourceAddress::Ip("192.168.1.100:5961".into()),
-};
-println!("{}", source.name);
-if let SourceAddress::Ip(address) = &source.address {
+let source = Source::new("CAMERA (Program)")
+    .with_address(SourceAddress::Ip("192.168.1.100:5961".into()));
+println!("{}", source.name());
+if let Some(SourceAddress::Ip(address)) = source.address() {
     println!("at {address}");
 }

-let host = source.ip_address();
+let host = source.host();
```

- `SourceAddress::None` is removed: `address()` returns `None` for a source
  without an address. `Source` and `SourceAddress` no longer implement
  `Default`.
- `Source::host` returns what `ip_address` did, which for a URL source is a
  host name.

**`Tally`, `ReceiverStatus` and `ConnectionStats` have getters instead of
public fields,** with the fields' names:

```diff
-if tally.on_program {
+if tally.on_program() {
     println!("on air");
 }
-let connections = stats.connections;
-let dropped = stats.video_frames_dropped;
+let connections = stats.connections();
+let dropped = stats.video_frames_dropped();
```

`Tally::new(on_program, on_preview)` is unchanged, and all three types are now
`Copy`.

**`SourceCache::find_by_host` takes the runtime handle.** The cache no longer
starts NDI by itself:

```diff
 let cache = SourceCache::new();
-let camera = cache.find_by_host("192.168.1.100", Duration::from_secs(5))?;
+let camera = cache.find_by_host(&ndi, "192.168.1.100", Duration::from_secs(5))?;
```

### Frames

**Dimensions and counts are unsigned, and sizes are `usize`.** Widths,
heights, frame-rate parts, sample rates and channel and sample counts are
`u32`; line strides, channel strides and buffer lengths are `usize`. 2.0 used
`i32` for all of them. A value the SDK cannot represent, above `i32::MAX`, is
refused before it reaches the SDK.

```diff
-let stride = PixelFormat::BGRA.try_line_stride(1920)? as usize;
-let len = PixelFormat::BGRA.try_buffer_size(1920, 1080)?;
-let nv12_len = PixelFormat::NV12.info().try_buffer_len(1920, 1080)?;
+let stride = PixelFormat::Bgra.line_stride(1920)?;
+let len = PixelFormat::Bgra.buffer_len(1920, 1080)?;
+let nv12_len = PixelFormat::Nv12.info().buffer_len(1920, 1080)?;
```

**Frame rates are `FrameRate` values, and builders start from the frame
type.** `VideoFrameBuilder::new()`, `AudioFrameBuilder::new()` and the
builders' `Default` are removed:

```diff
-let mut frame = VideoFrameBuilder::new()
+let mut frame = VideoFrame::builder()
     .resolution(1280, 720)
-    .frame_rate(30_000, 1_001)
-    .aspect_ratio(16.0 / 9.0)
+    .frame_rate(FrameRate::new(30_000, 1_001)?)
+    .picture_aspect_ratio(16.0 / 9.0)
     .build()?;
-println!("{}/{}", frame.frame_rate_n(), frame.frame_rate_d());
-frame.set_frame_rate(60, 1)?;
+let rate = frame.frame_rate();
+println!("{}/{}", rate.numerator(), rate.denominator());
+frame.set_frame_rate(FrameRate::new(60, 1)?);
```

`frame_rate()` replaces `frame_rate_n()` and `frame_rate_d()` on `VideoFrame`,
`VideoRef` and `BorrowedVideoFrame`, and `BorrowedVideoFrameBuilder::frame_rate`
takes a `FrameRate` too. `FrameRate::new` checks both parts, so
`set_frame_rate` no longer returns a `Result`. `VideoFrame`, `AudioFrame` and
`MetadataFrame` no longer implement `Default`; build a frame instead.

**The audio builder's setters are named after the frame's getters:**

```diff
-let audio = AudioFrameBuilder::new()
-    .format(AudioFormat::FLTP)
+let audio = AudioFrame::builder()
     .sample_rate(48_000)
-    .channels(2)
-    .samples(1_600)
+    .num_channels(2)
+    .num_samples(1_600)
     .build()?;
-let stride = audio.channel_stride_in_bytes() as usize;
+let stride = audio.channel_stride_bytes();
```

`AudioFrameBuilder::format` is removed: `AudioFormat::Fltp` is the only format
and every audio frame uses it. `channel_stride_bytes` replaces
`channel_stride_in_bytes` on received audio too.

**Timecodes are `Timecode` values, and timestamps are only read:**

```diff
-frame.set_timecode(0);
-let ticks: i64 = frame.timecode();
+frame.set_timecode(Timecode::from_ticks(0));
+let ticks: i64 = frame.timecode().ticks();

-let metadata = MetadataFrame::with_data("<ptz_info/>", 0)?;
+let metadata = MetadataFrame::new("<ptz_info/>")?.with_timecode(Timecode::from_ticks(0));
```

- Every frame you build starts with `Timecode::SYNTHESIZE`, the SDK's request
  to generate a timecode, as in 2.0, where it was the raw value `i64::MAX`.
- `MetadataFrame::new` takes the text. The empty `MetadataFrame::new()` and
  `MetadataFrame::with_data` are removed.
- A received frame's `timestamp()` returns `Option<SdkTimestamp>`, which is
  `None` when the SDK has no timestamp for it; 2.0 returned the SDK's raw
  `i64`. The SDK generates the timestamp when it sends a frame, so
  `VideoFrame::set_timestamp`, the builders' `timestamp` setters and
  `BorrowedVideoFrame::timestamp` are removed. Delete calls to them.

**Pixel formats convert through `FourCc`.** `PixelFormat`, `ScanType` and
`AudioFormat` no longer convert to and from the SDK's raw `u32` and `i32`
values:

```diff
-let fourcc: u32 = PixelFormat::UYVY.into();
-let format = PixelFormat::try_from(fourcc)?;
+let fourcc = FourCc::from(PixelFormat::Uyvy);
+let format = PixelFormat::try_from(fourcc)?;
```

`fourcc.raw()` is the `u32`, and `FourCc::from_raw` makes a `FourCc` from
one.

**The first plane's stride is a `usize`:**

```diff
-let stride = match frame.line_stride_or_size() {
-    LineStrideOrSize::LineStrideBytes(stride) => stride as usize,
-};
+let stride = frame.line_stride_bytes();
```

`LineStrideOrSize` is removed. `line_stride_bytes` is on `VideoFrame`,
`VideoRef` and `BorrowedVideoFrame`.

**Borrowed frames convert to owned ones with `try_to_owned`:**

```diff
-let owned = video_ref.to_owned()?;
+let owned = video_ref.try_to_owned()?;
```

This applies to `VideoRef` and `AudioRef`, including FrameSync's;
`MetadataFrameRef::to_owned` cannot fail and keeps its name.

**`replace_data` hands the buffer back on failure.** `VideoFrame::replace_data`
and `AudioFrame::replace_data` return the refused buffer in a `Rejected`, which
converts into an `Error`, so `?` keeps working. Call `into_inner` on the error
to reuse the buffer.

**`VideoFrame::from_raw` is removed.** Frames come from a capture or a
builder.

### Receiving

**A capture that times out returns `None`:**

```diff
-let frame = receiver.video().capture(Duration::from_secs(5))?;
+let Some(frame) = receiver.video().capture(Duration::from_secs(5))? else {
+    return Ok(()); // nothing arrived within the timeout
+};

-if let Some(frame) = receiver.video().try_capture(Duration::from_millis(100))? {
+if let Some(frame) = receiver.video().capture(Duration::from_millis(100))? {
     println!("{}x{}", frame.width(), frame.height());
 }

-if let Some(audio) = receiver.audio().try_capture_ref(Duration::from_millis(100))? {
+if let Some(audio) = receiver.audio().capture_ref(Duration::from_millis(100))? {
     println!("{} samples", audio.num_samples());
 }
```

- `Error::FrameTimeout` is removed. A `match` arm for it becomes the `None`
  case.
- `try_capture` is removed and `try_capture_ref` is `capture_ref`. 2.0's
  `try_capture` and `try_capture_ref` made one SDK call and could return `None`
  early, while the SDK synchronized a new connection or reported a status
  change. `capture` and `capture_ref` capture again until a frame arrives or
  the whole timeout is spent, as 2.0's `capture` did, so a loop that polled
  with a short timeout may now wait that long for each frame. `Duration::ZERO`
  still makes one attempt. A status or source change a capture passes over is
  kept for `Receiver::poll_event`.
- The async `AsyncCapture::capture` returns `Option` in the same way, and its
  `try_capture` is removed.
- `CaptureKind::ref_to_owned` is no longer public; use `try_to_owned` on the
  reference.

**PTZ control is a separate handle.** `Receiver::ptz()` returns a `Ptz`, whose
methods are the `ptz_*` methods without the prefix:

```diff
-if receiver.ptz_is_supported() {
-    receiver.ptz_zoom(0.5)?;
-    receiver.ptz_store_preset(3_i32)?;
-    receiver.ptz_recall_preset(3_u32, 1.0)?;
-    receiver.ptz_exposure_manual_v2(0.5, 0.2, 0.1)?;
+let ptz = receiver.ptz();
+if ptz.is_supported() {
+    ptz.zoom(0.5)?;
+    ptz.store_preset(3_u8)?;
+    ptz.recall_preset(3_u8, 1.0)?;
+    ptz.exposure_manual_detailed(0.5, 0.2, 0.1)?;
 }
```

`ptz_exposure_manual_v2` is `exposure_manual_detailed`. Both preset methods
take the preset as a `u8` in `0..=99`. A command the SDK rejects is
`Error::NativeOperationFailed`, which names the SDK function.

**Tally and upstream metadata report what the SDK reports:**

```diff
-let _connected: bool = receiver.set_tally(&Tally::new(true, false));
+receiver.set_tally(Tally::new(true, false));

-if !receiver.send_metadata(&metadata) {
-    eprintln!("not connected");
-}
+match receiver.send_metadata(&metadata) {
+    Err(Error::NotConnected) => eprintln!("not connected"),
+    result => result?,
+}
```

- `set_tally` takes the `Tally` by value and returns nothing. The SDK keeps
  the tally and sends it to every source the receiver connects to, so a
  receiver that is not connected yet loses nothing.
- `send_metadata` returns `Error::NotConnected` where 2.0 returned `false`.

**`Receiver::poll_status_change` is removed.** `poll_event` returns the same
status, and it is the only poller, so two pollers no longer compete for the
same notification:

```diff
-if let Some(status) = receiver.poll_status_change(timeout)? {
-    println!("{} connections", status.connections);
+if let Some(ReceiverEvent::StatusChanged(status)) = receiver.poll_event(timeout)? {
+    println!("{} connections", status.connections());
 }
```

`poll_event` also returns the source-change events that `poll_status_change`
skipped, so match the variant you want.

### FrameSync

**The owned captures take the short names.** `capture_video` and
`capture_audio` now return owned frames, as `capture_video_owned` and
`capture_audio_owned` did, and the borrowing captures are `capture_video_ref`
and `capture_audio_ref`:

```diff
-if let Some(video) = framesync.capture_video(ScanType::Progressive)? {
+if let Some(video) = framesync.capture_video_ref(ScanType::Progressive)? {
     println!("{}x{}", video.width(), video.height());
 }
-let owned = framesync.capture_video_owned(ScanType::Progressive)?;
+let owned = framesync.capture_video(ScanType::Progressive)?;

-let request = FrameSyncAudioRequest::capture_with(Some(48_000), 2, 1_600)?;
-let audio = framesync.capture_audio(request)?;
-let owned_audio = framesync.capture_audio_owned(request)?;
+let request = FrameSyncAudioRequest::capture_at(48_000, 2, 1_600)?;
+let audio = framesync.capture_audio_ref(request)?;
+let owned_audio = framesync.capture_audio(request)?;
```

- A 2.0 call to `capture_video` or `capture_audio` whose result is used only
  through methods both kinds of frame have still compiles, and now copies the
  frame. Rename it to the `_ref` form to keep borrowing the SDK's buffer.
- `FrameSyncAudioRequest::capture_with(Some(rate), channels, samples)` is
  `capture_at(rate, channels, samples)`, and `capture_with(None, channels,
  samples)` is `capture(channels, samples)`. All three take `u32`.
- `audio_queue_depth` returns a `u32`.
- `FrameSync::new` hands the receiver back in a `Rejected` when the SDK does
  not create the FrameSync. `?` converts that into an `Error`, as before.

### Sending

**Video sends return a `Result`:**

```diff
-sender.send_video(&frame);
-if let Some(previous) = sender.send_video_async(next) {
+sender.send_video(&frame)?;
+if let Some(previous) = sender.send_video_async(next)? {
     drop(previous);
 }
```

Every video send first checks that the sender's runtime can send the frame's
pixel format. Every NDI 6 runtime can send the formats 2.0 had; the planar
4:4:4 formats new in 3.0 need `RuntimeFeature::Planar444Video`, and a frame in
one of them is refused with `Error::UnsupportedCapability`. `send_video_async`
hands a refused frame back in a `Rejected`; `into_inner` recovers it unsent.

**Borrowed frames are made with the builder:**

```diff
-let frame = BorrowedVideoFrame::try_from_uncompressed(&pixels, 1920, 1080, PixelFormat::BGRA, 30, 1)?
-    .with_picture_aspect_ratio(16.0 / 9.0)?;
+let frame = BorrowedVideoFrame::builder(&pixels, 1920, 1080, PixelFormat::Bgra)
+    .frame_rate(FrameRate::new(30, 1)?)
+    .picture_aspect_ratio(16.0 / 9.0)
+    .build()?;
-let fourcc: u32 = frame.fourcc();
-let len = frame.validated_data_len();
+let fourcc = FourCc::from(frame.pixel_format());
+let len = frame.data().len();
```

- The builder's `line_stride` takes a `usize`, `frame_rate` a `FrameRate` and
  `timecode` a `Timecode`, and its `timestamp` is removed.
- `BorrowedVideoFrame::data()` returns the frame's storage, rows and padding,
  which `validated_data_len()` measured. 2.0's `data()` returned the whole
  buffer passed to the builder, including any bytes after the frame.

### Errors

**Six error variants are removed and one is renamed:**

| 2.0 | 3.0 |
| --- | --- |
| `InvalidConfiguration` | `InvalidInput`, for the same values and for the new APIs' input. |
| `FrameTimeout` | `Ok(None)` from the capture; see [Receiving](#receiving). |
| `NullPointer` | `NativeOperationFailed`, naming the SDK function that supplied no source descriptor. |
| `PtzCommandFailed` | `NativeOperationFailed`, naming the PTZ function. |
| `Timeout` | `UnexpectedSdkResult`, for the negative count that `Sender::connection_count` can get from the SDK. |
| `SourceUnavailable`, `Disconnected` | Nothing: 2.0 never returned them. Delete `match` arms that name them. |

`Error::Io`, which 2.0 never returned, now exists only with the `file-io`
feature: the File API returns it for operating-system errors. Delete `match`
arms that name it in a build without that feature.

Two results of `Ndi::new()` changed:

- A missing NDI library is `Error::RuntimeLoadFailed` from `Ndi::new()`. With
  2.0 the program did not start.
- A runtime that does not start because the CPU lacks instructions it needs is
  `Error::UnsupportedCpu`. With 2.0 it was `Error::InitializationFailed`.

A finder, receiver, sender or FrameSync that the SDK does not create is
`Error::NativeOperationFailed`, whose `operation` names the creating function,
such as `"NDIlib_send_create"`. With 2.0 it was `Error::InitializationFailed`.

`Error` has new variants, listed under [New errors](#new-errors). The enum
was already `#[non_exhaustive]`, so a `match` on it already has a wildcard arm
and keeps compiling unless it names one of the removed variants.

### Timeouts

`MAX_TIMEOUT` is one millisecond shorter, `u32::MAX - 1` milliseconds, because
the SDK reads `u32::MAX` as a wait without a limit. Code that passes
`MAX_TIMEOUT` keeps working; a hard-coded `u32::MAX` milliseconds is refused
with `Error::InvalidInput`. Every wait is rounded up to whole milliseconds, so
a wait shorter than a millisecond now blocks for one instead of polling; pass
`Duration::ZERO` to poll.

### Linking

**The build no longer links the NDI library** for Windows, macOS, Linux and
Android targets; 2.0 passed it to the linker. Code that declares its own NDI
functions with `extern "C"`, and C or C++ code that calls NDI, must now link
the library itself, for example with its own `cargo:rustc-link-lib`. Calls made
through this crate need nothing: it opens the library at run time and does not
make its symbols visible to the rest of the program.

The library search order changed as well, and it now looks for either SDK
edition; see [Where the library is found](#where-the-library-is-found) and
[Both editions are searched for](#both-editions-are-searched-for).

### Everything else

Everything else in 3.0 is an addition: runtime selection and capability
queries, routing, Discovery Server objects, NDI 6.4 formats and receiver
controls, checked audio and video conversions, and the optional `advanced` and
`file` modules (Cargo features `advanced` and `file-io`). The
[README](../../README.md) introduces each one.

## Building

A 2.0 build ran bindgen against an installed NDI SDK and linked the SDK's
library. A 3.0 build for Windows, macOS, Linux or Android does neither, unless
the `advanced` feature finds an Advanced SDK, in which case it runs bindgen on
that SDK's Advanced-only headers. The other bindings are part of the crate.

- Build machines and CI jobs that only compile no longer need the NDI SDK or
  LLVM/`libclang`, except to build the `advanced` feature's native code. A
  machine needs an NDI runtime library only where tests or the program itself
  use NDI.
- What is installed on the build machine no longer changes the program. A
  2.0 build on a machine with the Advanced SDK linked the Advanced library; a
  3.0 program looks for the library of either edition when it runs; see
  [Both editions are searched for](#both-editions-are-searched-for).
- Cross-compiling needs no target SDK. Version 2.0 refused to cross-compile
  without `NDI_SDK_DIR`; 3.0 does not need it for these targets.
- The documentation builds without an SDK. The crate's API reference link now
  points to [docs.rs](https://docs.rs/grafton-ndi).

`NDI_SDK_DIR` is read at build time only by two kinds of build:

1. A build with the `advanced` feature, to find the Advanced SDK headers.
2. A build for iOS, tvOS or visionOS, to find the static library. Support for
   these targets is new in 3.0; they link NDI at build time and require the
   variable.

Every other build ignores it, so a value left over from 2.0 no longer matters
there. In the two builds that read it, a set `NDI_SDK_DIR` must name an NDI SDK
installation: a directory whose `include` (or `Include`) directory contains
`Processing.NDI.Lib.h`, the spelling the NDI SDK installers use. A stale value
fails those builds:

```text
NDI_SDK_DIR is not an NDI SDK installation: Cannot read SDK directory /old/path: No such file or directory (os error 2)
```

Unset the variable on machines that no longer have an SDK. When it is unset,
an `advanced` build looks only in the Advanced SDK installer's default
directory, no longer in the Standard SDK's, and continues without the Advanced
declarations if it finds none. It does not notice an SDK that is installed
there after the first build.
Set `NDI_SDK_DIR`, which triggers a rebuild, or run `cargo clean -p grafton-ndi`.

## Running

### Selecting and starting are separate steps

Using NDI takes two steps. `Runtime::select` loads the NDI library and pins it
for the rest of the process, without starting NDI. `Runtime::initialize` starts
NDI and returns the `Ndi` handle. `Ndi::new()` does both with the default
options, and `Ndi::with_options` with the options it is given, so code that
only calls `Ndi::new()` needs no other change.

Nothing else selects a runtime. `Ndi::is_running()`, for one, loads nothing.

Selecting first lets a program inspect the library before it starts NDI:

```rust
use grafton_ndi::{Runtime, RuntimeOptions};

fn main() -> grafton_ndi::Result<()> {
    let runtime = Runtime::select(&RuntimeOptions::default())?;
    println!("NDI {}", runtime.info().raw_version());
    if !runtime.is_supported_cpu() {
        eprintln!("this CPU cannot run the selected NDI runtime");
    }
    let ndi = runtime.initialize()?;
    println!("started: {ndi:?}");
    Ok(())
}
```

### A missing runtime is an error value

With 2.0, a program whose NDI library could not be found did not start: the
operating system's loader stopped it before `main` ran. With 3.0 the program
starts, and a library that cannot be found is reported by the call that
selects it:

```rust
use grafton_ndi::{Error, Ndi};

fn main() {
    match Ndi::new() {
        Ok(ndi) => println!("NDI {} is ready", ndi.info().raw_version()),
        Err(Error::RuntimeLoadFailed(reason)) => {
            // `reason` lists every location tried and why each failed.
            eprintln!("NDI is not installed: {reason}");
        }
        Err(Error::UnsupportedCpu) => eprintln!("NDI cannot run on this CPU"),
        Err(error) => eprintln!("NDI could not be initialized: {error}"),
    }
}
```

This lets an application start without NDI and offer it as an optional
feature. Selection is retryable: if the first attempt fails, a later call
searches again, so a program can ask the user to install the runtime and try
once more.

### Where the library is found

Version 2.0 left the search to the operating system: the executable's run path,
`LD_LIBRARY_PATH` or `PATH`, and the system library directories. Version 3.0
tries these locations in order and takes the first usable library:

1. The directory that contains the running executable.
2. The directory named by the `NDI_RUNTIME_DIR_V6` environment variable.
3. The operating system's search, as in 2.0. On macOS the name is first tried
   as `@rpath/<name>`.

A setup that worked with 2.0 keeps working through step 3, with one difference
to check: steps 1 and 2 now come first. If `NDI_RUNTIME_DIR_V6` is set on a
machine, the library in that directory is used even when a different one is
on the loader's path. `ndi.info().library_path()` reports which file was
loaded.

A plug-in or extension module is the exception. Step 1 is the host program's
directory, not the plug-in's, and on Windows step 3 does not search the
plug-in's directory either, so a library that 2.0 found beside the plug-in may
not be found. Set `NDI_RUNTIME_DIR_V6`, or pass the library's path as shown
under [Deploying](#deploying).

The error for a failed search names each location:

```text
Failed to load an NDI library: no usable NDI runtime; tried /opt/app/libndi.so.6 (next to the executable): not found; /opt/app/libndi_advanced.so.6 (next to the executable): not found; libndi.so.6 (system library search): dlopen failed: libndi.so.6: cannot open shared object file: No such file or directory; libndi_advanced.so.6 (system library search): dlopen failed: libndi_advanced.so.6: cannot open shared object file: No such file or directory
```

### One library per process

The first library that is selected successfully stays selected, and loaded,
for the life of the process, including after the last `Ndi` handle is dropped.
Starting and stopping NDI still follow the handles as in 2.0. Asking for a
different library afterwards returns `Error::RuntimeConflict`.

### Both editions are searched for

The Standard and Advanced SDKs have different library file names, for example
`libndi.so.6` and `libndi_advanced.so.6` on Linux. Unless the program asks for
one edition, each location in the search is tried for both names before the
next location, so the program finds whichever runtime the machine has. A build
with the `advanced` feature, or with `file-io` on Linux, macOS or Android, where
the File library needs the Advanced runtime, tries the Advanced name first at
each location; other builds try the Standard name first.

Version 2.0 on Linux and Android linked the Advanced library when the build
machine had the Advanced SDK, and such a program needed the Advanced runtime
wherever it ran. A 3.0 program built on the same machine also runs where only
the Standard runtime is installed. A program that needs Advanced SDK
operations should say so, and fail at selection instead of later:

```rust
use grafton_ndi::{Ndi, RuntimeOptions, SdkEdition};

fn main() -> grafton_ndi::Result<()> {
    let options = RuntimeOptions::default().edition(SdkEdition::Advanced);
    let ndi = Ndi::with_options(&options)?;
    println!("loaded the {:?} runtime", ndi.info().edition());
    Ok(())
}
```

Requesting `SdkEdition::Advanced` searches only for the Advanced file name and
requires the loaded library to be an Advanced SDK runtime. Requesting
`SdkEdition::Standard` searches only for the Standard file name; an Advanced
runtime found under it meets a Standard request.

### A rejected library stays loaded

A library that loads and is then found unusable is rejected, and the search
moves on. The rejected library stays loaded, because a native library cannot
be unloaded safely. If the operating system's own search in step 3 then
matches the library name to that rejected module, it returns the module again
instead of looking further. The error names the rejected file. Remove or fix
that file, or select the right one with an explicit path as shown under
[Deploying](#deploying).

## New errors

Every variant below is new in 3.0, except `InvalidInput`, which is 2.0's
`InvalidConfiguration` renamed.

| Variant | Returned when |
| --- | --- |
| `RuntimeLoadFailed` | No usable NDI library could be loaded. Returned by `Runtime::select`, `Ndi::new` and `Ndi::with_options`, and by `file::FileApi::open` for the File library. |
| `RuntimeConflict` | `Runtime::select` or `Ndi::with_options` names a library other than the one already selected, or requires the Advanced SDK when the selected library is a Standard one. `file::FileApi::open` returns it for a File library that cannot be used with the selected runtime. |
| `UnsupportedCpu` | The runtime did not start and reports that this CPU cannot run it. Returned by `Runtime::initialize`, `Ndi::new` and `Ndi::with_options`. |
| `UnsupportedCapability` | An optional operation is not available with the selected library or in this build. `feature` names it, `reason` is the `CapabilityUnavailable` that `capabilities()` reports for it, and `detail` gives the evidence. |
| `NativeOperationFailed` | The SDK refused an operation, such as a PTZ command, a routing change or an advertiser registration, or did not create a finder, receiver, sender or other object. `operation` names the SDK function. |
| `NotConnected` | `Receiver::send_metadata`, or the `send_metadata` of an `advanced` packet receiver, sent nothing because the receiver is connected to no source. |
| `InvalidInput` | A value passed to the crate is out of range, malformed or conflicts with another setting, such as a timeout above `MAX_TIMEOUT` or a PTZ value outside its range. |
| `UnexpectedSdkResult` | A value the SDK returned breaks its documented contract, such as a negative connection count. |
| `ReceiverRequestNotAccepted` | `RecvListener::request_connect` or `request_disconnect` names a receiver the listener does not list as accepting connection requests. `advertised` is false when no listed receiver has the identifier yet. |
| `InvalidState` | With the `file-io` feature: a File API operation the recorder's or async handle's state does not allow. The `StateError` says which state and whether a retry can succeed. |

Operations that existed in 2.0, used with the formats and settings 2.0 had,
call only functions that every supported NDI 6 library exports. They do not
return `UnsupportedCapability`. A library that lacks one of those functions is
rejected when it is selected.

`Error::InitializationFailed` now means only that the library loaded and the
SDK refused to start, for any reason other than the CPU, or that the process
holds so many `Ndi` handles that their count would overflow. An object the SDK
does not create is `Error::NativeOperationFailed`, and a Discovery Server
address it refuses is `Error::InvalidInput`.

## Deploying

The executable no longer lists the NDI library among its dependencies. Tools
that collect a program's libraries by inspecting the executable will not find
it, so add the NDI library to your package explicitly. Three arrangements
work, and they can be combined:

- **Ship the library beside the executable.** Put the file with the name from
  the [README table](../../README.md#finding-the-runtime) in the executable's
  directory. It is found first, whatever else is installed.
- **Use an installed runtime.** Set `NDI_RUNTIME_DIR_V6` to the runtime's
  directory, or install the library where the operating system's loader finds
  it.
- **Name the file.** Pass an absolute path. Nothing else is tried, so a wrong
  path is reported instead of being hidden by a fallback:

```rust
use grafton_ndi::{Ndi, RuntimeOptions};

fn main() -> grafton_ndi::Result<()> {
    let options = RuntimeOptions::default().library_path("/opt/ndi/lib/libndi.so.6");
    let ndi = Ndi::with_options(&options)?;
    println!("loaded {:?}", ndi.info().library_path());
    Ok(())
}
```

Loading a library runs its native code. Load only NDI libraries you trust. The
search reads `NDI_RUNTIME_DIR_V6` and the executable's directory, so a program
that runs with privileges its user does not have should pass an explicit path.

## Tests and continuous integration

Tests that use NDI now need the runtime only when they run. A job that only
builds, lints or documents your crate needs no NDI installation at all. A job
that runs NDI tests needs the runtime library in one of the locations above,
for example through `NDI_RUNTIME_DIR_V6`.

## Optional capabilities

NDI libraries differ in what they export, and the new APIs check before they
call. To check yourself, ask the selected runtime:

```rust
use grafton_ndi::{Ndi, RuntimeFeature};

fn main() -> grafton_ndi::Result<()> {
    let ndi = Ndi::new()?;
    if ndi.capabilities().supports(RuntimeFeature::ReceiveDelay) {
        println!("receiver delay controls are available");
    }
    // Or fail with the reason.
    ndi.require_feature(RuntimeFeature::Routing)?;
    Ok(())
}
```

See [Runtime capabilities](../../README.md#runtime-capabilities-and-optional-apis)
in the README for the list and what each reason means.
